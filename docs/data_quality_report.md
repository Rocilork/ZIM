# Отчёт о качестве данных. Seoul Bike

## 1. Контекст

**Аналитический вопрос** (из [Project Brief](project_brief.md)): как различается почасовой
спрос на велосипеды в Сеуле по сезону, часу суток и типу дня (рабочий, выходной,
праздничный)?

**Входной S3-путь:**

```text
s3://raw/seoul_bike/ingested_on=2026-11-12/SeoulBikeData.csv
```

**Смысл одной строки:** один час работы системы велопроката — одно значение часа (0–23)
в одни календарные сутки. Набор содержит 8760 строк: 24 часа × 365 дней.

**Бизнес-ключ.** Надёжного естественного ключа в источнике нет: данные агрегированы по
часам, отдельная поездка не видна. Проверяется уникальность сочетания `observed_on` + `hour`
как подтверждение заявленной гранулярности. Это **не** доказательство уникальности реальных
событий: несколько разных поездок одного часа неразличимы по построению набора. Поэтому
искусственный идентификатор строки не создавался и `DISTINCT` для «уникальности» не
применялся.

**Распределение спроса по часам суток** (число записей одинаково — по 365 на каждый час):

| Час | 0 | 4 | 8 | 12 | 17 | 18 | 23 |
|---|---|---|---|---|---|---|---|
| Средний спрос | 541.5 | 132.6 | 1015.7 | 699.4 | 1138.5 | 1502.9 | 671.1 |

**Два значимых наблюдения.**

1. **Нулевой спрос — это остановка сервиса, а не отсутствие спроса.** Все 295 записей
   с `rented_bike_count = 0` имеют `functioning_day = false`, и обратное тоже верно: при
   работающем сервисе нулевого спроса не встречается ни разу (`sum_rented = 6 172 314`
   на 8465 работающих часов, минимум 2). Ноль описывает закрытый сервис — 295 часов
   в 13 днях с 2018-04-11 по 2018-11-09. Если такие часы не отделять, средний спрос
   по любому срезу окажется заниженным. Для этого в `staging` добавлен признак
   `service_closed`.

2. **Два подозрительных значения в погодных полях.** Влажность ровно 0 % встречается
   17 раз, причём все они приходятся на май и ни разу не сопровождаются осадками; снег
   при температуре выше 5 °C встречается 14 раз. Оба случая похожи на сбои датчиков или
   сдвиг времени наблюдения. Они не мешают основной метрике (число аренд в этих часах
   выглядит достоверным), но способны исказить уточняющий вопрос о связи погоды и спроса,
   поэтому записи помечены признаками.

## 3. Правила и результаты

Описания правил, их критичность и связь с задачей приведены в ноутбуке

превышение фиксируется, когда число нарушений больше порога.

| `closed_service_has_no_demand` | 295 | 0 | 0.000 % | count ≤ 0 | Не превышен | quarantine |
| `humidity_zero_is_suspicious` | 8 760 | 17 | 0.194 % | count ≤ 0 | **Превышен** | flag |
| `snowfall_requires_cold` | 8 760 | 14 | 0.160 % | count ≤ 0 | **Превышен** | flag |

Семь правил совместно покрывают требуемые свойства: уникальность (правило 1), полноту
(правило 2), допустимость значений (правила 3, 4) и согласованность связанных полей
(правила 5, 6, 7).

**Решения по записям.** Карантин остался пустым: ни одно критическое правило не нарушено,
поэтому исключать записи не потребовалось. По правилам-предупреждениям 17 записей
с нулевой влажностью и 14 записей со снегом при тёплой температуре **сохранены** в
`staging` с признаками нарушений, а не удалены: значение, вызывающее сомнение, относится
к погодному показателю, тогда как число аренд в этих часах достоверно и нужно для основной
метрики. Удаление таких строк изменило бы число часов и сместило бы средний спрос.

Отдельно добавлен описательный признак `service_closed` (295 строк) — это не нарушение,
а характеристика записи: часы остановки сервиса нужно исключать из расчёта среднего спроса.

## 4. Подготовленные данные

| Результат | S3-путь |
|---|---|
| `staging.parquet` | `s3://staging/seoul_bike/source_ingested_on=2026-11-12/staging.parquet` |
| `quarantine.parquet` | `s3://staging/seoul_bike/source_ingested_on=2026-11-12/quarantine.parquet` |

Логическая дата в пути совпадает с `ingested_on` исходного raw-объекта
(2026-11-12), а не с датой выполнения ноутбука.

**Баланс строк:** `raw = staging + карантин` → 8 760 = 8 760 + 0. Записи не теряются
и не добавляются при обработке.

**Фактические преобразования и добавленные признаки:**

- Переименование всех 14 полей при чтении (см. таблицу соответствия в разделе 2).
  Исходные имена неудобны в SQL и содержат знак градуса. Значения не изменялись.
- `service_closed` = `NOT functioning_day` — признак часа остановки сервиса.
- `quality_humidity_zero_is_suspicious_violated` — признак нарушения правила 6 (17 строк).
- `quality_snowfall_requires_cold_violated` — признак нарушения правила 7 (14 строк).
- В карантин добавлены поля `quality_rule_ids` и `quarantine_reason`. Несколько
  идентификаторов перечисляются через `;`. Поскольку карантин пуст, файл создан
  с корректной схемой и нулём строк.

**Проверка критических правил на подготовленном наборе.** После повторного чтения
`staging.parquet` из S3: критических нарушений 0, повторов ключа 0, неверных признаков 0
(влажность, снег, сервис), строк карантина без причины 0. Исходный объект в `raw`
не изменялся.

Количества совпали, повторных объектов в префиксе не появилось, ошибок при выполнении
не было.

**Ограничения дальнейшего анализа:**

- Данные агрегированы по часам: длительность поездки, маршрут и поведение отдельного
  пользователя по ним не изучаются, а фактический спрос может быть выше наблюдаемого —
  неудачные попытки аренды и нехватка велосипедов в данных отсутствуют.
- Набор охватывает один город и один непрерывный год, пересекающий два календарных года
  (2017 и 2018). Сравнение «2017 против 2018» по этим данным некорректно: каждый год
  представлен неполным набором месяцев.
- Погодные показатели — наблюдения метеослужбы, а не условия в точке аренды. Связь
  погоды и спроса описывается по числам, но не доказывает причину.
- 17 часов с нулевой влажностью и 14 часов со снегом при тёплой температуре сохраняют
  сомнительные погодные значения. При расчёте связи по влажности или осадкам эти строки
  следует исключать по признакам.
